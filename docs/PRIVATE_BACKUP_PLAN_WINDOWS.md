Use the operator's **existing** authorized database access, entered privately into tool prompts. Never embed passwords in command strings/URLs, source files or PowerShell history. Use TLS with verified server identity and the actual dashboard connection parameters. No new credential is minted without approval.

Prefer one database snapshot containing the approved data; independently timed schema/data/Auth dumps are not automatically consistent. Schedule an owner-approved quiet interval for application and Storage writes and schema changes. The export itself does not put the service into maintenance mode. Without a coordinated window/snapshot across DB and object storage, label the copy provisional and document the recovery gap. Read-only backups can consume connection/egress/CPU quotas; estimate size, use a single controlled connection/download stream, and stop before any quota/billing issue. Do not enable billing to continue.

SQL dumps do not contain Storage file bytes. CLI default schema dumps also need explicit data/role/managed-schema coverage review. A regular logical copy is not PITR and loses changes after its capture point. ## Beginner steps — execute only after the named approvals

1. Confirm source project and approved local folder. Record the operator, approved scope, quiet time and restore objective privately. Suggested initial goal: a verified recovery point before any hosted change; agree ongoing recovery frequency/acceptable downtime separately. A daily offline copy is only a proposed schedule, not an established service.
2. After tool approval, download from the official links, verify the signed installer/archive, and install only the approved utilities. Do not install a PostgreSQL server unnecessarily for export. Do not click any upgrade/payment option.
3. Open VeraCrypt → **Create Volume → Create an encrypted file container → Standard volume**. Choose a new file inside the approved folder, sized for current DB + all files + temporary/archive space with headroom. Never select a disk/partition or existing file. Keep supported encryption defaults and choose a long unique random passphrase privately. Follow the vendor wizard. The human enters/retains this new encryption credential; do not give it to Codex.
4. Select a free drive letter and mount the new container. Create the export run folder there. Confirm access is limited to the owner and the PC is physically controlled. Stop if drive encryption, sync/redirects, temp handling or space cannot be verified. Do not make broad permission changes without approval.
5. After **sensitive export approval**, the reviewed exporter uses PostgreSQL prompts/read-only Storage requests and writes only to that encrypted drive. Do not use the SQL Editor's CSV export or open dumps in a text editor. All verbose output/errors go to private encrypted logs; shared receipt contains only status/tool versions/omissions. No exporter is supplied as an unattended scheduled job in this preparation phase.
6. Reconcile manifests and tool exit statuses. Use 7-Zip → **Add to archive**, format **7z**, encryption **AES-256**, **Encrypt file names** enabled; write the archive inside the mounted encrypted drive. Enter a separate long random archive password in the GUI; do not put it on a command line. Use **Test** to check readability and deliberately verify the wrong password cannot read contents. This is integrity/encryption checking, not a restore test.
7. Copy **only the encrypted archive** to the approved backup folder, then to an independently approved existing offline disk if available. Compare SHA-256 of encrypted copies using PowerShell `Get-FileHash`. Keep content/object manifests inside encryption. A single copy on the same PC does not protect against device loss/ransomware. No new hardware/cloud storage purchase is authorized; if no independent medium exists, record the unmet durability requirement.
8. Close tools and dismount normally; confirm the drive letter disappears. Keep the encrypted staging container until recovery verification/retention decisions are approved. Do not claim deleting plaintext securely erases SSD sectors; avoid unencrypted writes from the beginning. No automatic cleanup/deletion is part of this plan.
9. Approve and perform the isolated restore below. Record actual recovery duration, completeness and gaps. Only a verified copy and usable independent key close the recovery gate. Agree rotation/retention/periodic rehearsal later; do not overwrite the last verified copy.

## Key custody

Use unique generated passphrases, for example at least six randomly chosen words or 24+ random characters; do not reuse the Supabase login/database password. Keep encryption passwords in an existing trusted password manager protected by its own strong master key/MFA, with a sealed offline emergency copy in a separate secure location. Designate an authorized recovery custodian if appropriate; do not share through chat/email/Git or store the key beside the archive. A separately encrypted password-manager export is itself sensitive and requires approval before creation. Check emergency recovery can work without the lost PC or a circular dependency on this Supabase project. VeraCrypt header/recovery material must also be privately protected. Lost encryption credentials may make every copy permanently unrecoverable. Encryption at rest does not protect an unlocked volume from malware or an authorized user exporting its contents.
