# Demonstration and clinical-validation inventory

28 October 2026. This review records current behavior; it does not add features or authorize clinical use. Source references are relative to the repository root.

| Area | Current behavior / evidence | Pilot implication |
|---|---|---|
| Demo records | `src/data/seed.ts` creates fictional Iraqi names, fabricated phone-format examples, medications, reactions, messages, refills and labs. `/demo` has dedicated session storage and role simulation. | These are synthetic examples, not verified patient histories or actual account permissions. Phone examples are not an officially reserved number range and must never be contacted. Never import the demo dataset as clinical records. |
| Demo files | `src/pages/Records.tsx` keeps demo file bytes in a module-memory map; metadata survives in tab-session state. | File bytes disappear on reload. This is deliberately different from private hosted Storage. |
| Connected tenancy | Auth, memberships, active subscription checks, RLS and transactional RPC exist. The current hosted project has one Auth account and two memberships. | Existing testing does not prove isolation between independent real Auth identities. Use the prepared five-account/two-test-tenant suite. |
| Staff read scope — R1 | Foundation `tenant_read` policies permit any active pharmacy member to read patient, allergy, medication, lab and audit rows. Storage bytes separately require owner/pharmacist. | Broader than Settings' follow-up-only description. A pharmacy/privacy lead must explicitly approve the field-level role matrix or narrow the policies before real patient data. Migration 005 does not change this. |
| Shared condition labels — R2 | `chronic_conditions` is globally readable to authenticated users; free-text condition names are inserted through patient saves (`001`, `002`). Patient-condition links remain tenant scoped. | Govern the shared taxonomy and prevent identifiable/free-text patient detail in labels, or use tenant-local labels. Do not treat this global catalog as private clinical text. |
| Allergy checking | Exact normalized ingredient identity only. No fuzzy brand resolution, combination-component parsing or inferred class cross-reactivity. | No comprehensive allergy/interactions/contraindication, renal/hepatic, pregnancy, excipient or dose-safety knowledgebase. Lack of warning is not clearance. Independent clinical validation is required. |
| Allergy review | Resolution retains the original record and ingredient check; unknown history is distinct from none-known. | Review notes do not establish clinical truth automatically. Human source verification remains required. |
| Critical overrides | Clinically important matches block routine dispensing; the exceptional path uses an owner role plus documented reason. | Ownership does not establish professional registration. Only a suitably authorized clinician may receive that role/path. Validate governance and exceptional decisions independently. |
| Catalog and dosage | Manual ingredient identifiers and recorded prescriptions; supply arithmetic uses user-confirmed dose/frequency/quantity. | Catalog identity, formulation mapping and prescription validity are not clinically certified. No automatic prescribing or evidence of treatment suitability. |
| Refill estimates | Dates equal recorded date plus confirmed days supplied; unknown supply is supported for irregular schedules. | Estimates ignore stock on hand, other pharmacies and actual ingestion. They do not establish adherence. |
| Configurable thresholds — R3 | Settings persists `thresholds`, but current screens use `refillStatus`'s default seven-day threshold; no screen passes `settings.thresholds` (`clinical.ts:12`, `Settings.tsx`). | Custom values do not currently drive the displayed queues. Fix or explicitly limit the pilot to the documented default before relying on custom reminder settings. |
| Dispensing corrections — R4 | `adjustDispensing` stores an auditable correction (`commands.ts:16`, migration 002); no UI invokes this command and it does not recalculate medication refill state. | A complete correction/supersession and refill-reconciliation workflow is unfinished. Do not use incorrect transactions as clinical stock/refill evidence. Resolve before real dispensing pilot acceptance. |
| Consultations | Recorded internal messages, counseling notes and manual WhatsApp links. Seeded patient-message bubbles are fictional. | No real-time patient messaging portal, automated inbound integration, delivery receipt or automatic WhatsApp service. Opening WhatsApp does not prove sending/delivery. |
| Follow-ups | Manual scheduling and recorded contact outcomes with consent checks. | No automatic call/SMS/WhatsApp dispatch or unattended reminder scheduler. An explicit “unable to contact” outcome is not currently exposed; no-answer/reschedule are available. Assignment is free-text, not a verified licensed-practitioner directory. |
| Laboratory trends — R5 | Stored values and reference text, descriptive charts. `Records.tsx:13` groups series by test name and labels from the first result's unit. | Mixed units with the same test name can be plotted together. Add unit-consistent grouping/normalization and clinical acceptance before relying on trends. There is no automated diagnosis. |
| Documents — R6 | Private bucket, random paths, role policies, 5MB MIME limits, 60-second signed viewing links and authenticated downloads. | No magic-byte inspection, antivirus/PDF sanitization, tested retention policy or atomic Storage/database deletion. A failed second deletion step needs reconciliation. Do not upload real clinical documents before those controls are reviewed. |
| AI extraction | Disabled UI, provider/draft types and human-review guard exist. | No configured backend extraction provider, live OCR or connected extraction-review service. Manual entry is the usable workflow. Nothing is sent to an AI provider. |
| Analytics | Counts/value/denominators derive from stored records, with documented period scope. | Descriptive estimates are not clinical outcomes, verified adherence, profit accounting or a validated financial ledger. Advanced review-turnaround/comprehensive adherence reporting is not established. |
| Audit/retention — R7 | Clients cannot directly change audit rows; database administrators remain privileged. `retentionDays` is configuration metadata. | No cryptographic immutability, automatic compliant retention/deletion implementation or independent audit certification. Validate clinician access, shared-terminal cache/session behavior and retention rules. |
| Auth operations — R8 | Password sign-in works. Hosted signup is enabled, email confirmation enabled, site URL remains `http://localhost:3000`, redirect allow-list is empty. | Approve owner-provisioned signup policy, correct explicit testing URLs, and test recovery/logout/offboarding/MFA policy before a real pilot. There is no invitation/recovery UI workflow validated end to end. |
| Hosting/availability — R9 | Local preview only; Netlify is uncreated/unpublished. Supabase Free is used for synthetic development. | No uptime, backup/restore, incident response or clinical hosting suitability claim. Free inactivity pauses and manual export/restore requirements must be planned, without automatic upgrades. |
| Scale/devices | Four Edge viewport projects passed. Workspace loads all resource pages then refreshes them after writes. | No physical Android/Safari or large-tenant/concurrency acceptance yet. Plain HTTP LAN is not a full mobile workaround because `crypto.randomUUID()` requires a secure context. |
| SaaS subscriptions | Platform status/renewal/staff-limit administration exists with one development-free plan. | No commercial payment collection, billing reconciliation, automated upgrades or established paid service. Future payments require separate approval. |

R1–R9 are pilot review items, not changes made in this phase. See [SAAS_READINESS.md](SAAS_READINESS.md) for gates and [CLINICAL_SECURITY.md](CLINICAL_SECURITY.md) for established safety boundaries. None of the 16 demo browser checks should be relabelled as hosted multi-account or clinical validation.
